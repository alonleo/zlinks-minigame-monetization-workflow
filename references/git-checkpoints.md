# Git 检查点、阶段标签与推送协议

本协议适用于商业化工作流处理的每个游戏工程。提交、标签和推送是完成门禁的一部分，不是事后可选整理。每个工程独立执行；不得把多个游戏混入同一组检查点。

## 1. 开始前检查

在修改前记录仓库根目录、当前分支、`HEAD`、远程和工作区状态。确认当前分支可提交且存在可写远程；不得在 detached HEAD 上推进到阶段完成。

保留用户已有的未提交修改。每次只暂存本流程当前检查点所属的文件；无法与已有改动安全分离时停止提交并报告，不得用 `git add -A`、丢弃、覆盖或顺带提交无关改动。提交前检查暂存差异，并排除凭据、令牌、隐私数据、缓存和不应入库的构建产物。

## 2. 小需求点提交

每个规范化小需求点只有在实现完成、所需验证通过、台账更新且状态成为 `done` 后，才创建一次独立提交。不同需求不得为了省事合并提交；尚未验证、`partial`、`blocked`、`failed` 或 `not-applicable` 的项目不得使用“完成”提交信息。

提交信息采用可追踪格式：

```text
feat(<game-slug>): 完成并验证 <requirement-id> <short-summary>
```

修复、配置或资源类变更可以使用更准确的类型，但必须保留游戏标识、稳定需求 ID、完成和验证含义。提交后把 commit SHA 回填到需求台账。

## 3. 自统计检查点

自统计服务的接入、改造或核验必须有独立检查点。每个平台的自统计处理及其适用验证完成后，更新对应台账并创建提交；不能与平台官方 SDK/DNSDK 的处理结果含混为一个未经区分的结论。

```text
feat(<game-slug>): 完成并验证 <platform> 自统计 <scope>
```

若自统计本身就是一个已按第 2 节独立提交的小需求点，不重复创建空提交；在台账中将该 SHA 同时登记为自统计检查点。若后续统计核实阶段产生了新的网络证据或结论，则提交该阶段新增的脱敏证据与台账更新。

## 4. 大阶段里程碑

大阶段是 `requirements`、`recording`、`statistics`。只有该阶段所有适用平台和条目都满足本阶段的完成定义后，才能执行以下动作：

1. 更新并暂存阶段回执，回执列出所含小需求/平台、自统计检查点和对应 commit SHA；
2. 创建独立的阶段汇总提交：`milestone(<game-slug>): 完成 <stage> 阶段`；
3. 在该汇总提交上创建 annotated tag：`monetization/<game-slug>/<workflow-id>/<stage>-v<N>`；
4. 立即推送当前分支，再显式推送该标签；
5. 查询远程分支和标签，确认均指向预期提交，并把远程、分支、提交、标签和核验结果写入流程运行记录与最终回执。

阶段回执必须是仓库内可追踪文件，因此阶段汇总提交不得为空；提交前写入计划推送的远程、分支和标签。推送后的远程核验结果写入流程运行记录与最终回执，不为记录本次推送再改写已打标签的阶段回执，避免形成递归里程碑。`game-slug`、`workflow-id` 和标签各段只使用 Git ref 安全字符；`v<N>` 从远程和本地已有同阶段标签递增，不覆盖旧标签。

不得使用 force push，不得移动或复用已有标签，不得绕过 hooks。推送目标不明确、有多个候选远程、无权限、分支保护拒绝、提交/标签/推送失败或远端核验不一致时，保留已完成事实与本地 SHA，将阶段标为 `blocked` 或 `partial`，不能报告 `completed`。修复后从失败动作续做，避免重复创建含义相同的提交或标签。

## 5. 最终回执

每个工程最终列出：

- 各小需求点的 requirement ID、验证结论和 commit SHA；
- 各平台自统计检查点及 commit SHA；
- 每个大阶段的汇总 commit、annotated tag、远程和推送核验；
- 未提交、未打标签或未推送的原因及可续做动作。

小需求提交完成不等于阶段完成；本地阶段提交或本地标签存在也不等于阶段完成。只有远程分支与阶段标签核验通过，才能把对应大阶段报告为 `completed`。
