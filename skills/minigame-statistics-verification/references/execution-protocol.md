# 数据统计核实阶段执行协议

本阶段核实目标平台的统计集成和运行时真实上报。代码中存在调用、SDK 初始化成功或本地打印事件名都不能单独证明上报完成；每个要求统计的行为必须在对应通道中找到本次触发产生的外发请求、成功响应以及正确数据。

## 1. 确定平台与通道

先从信息表、构建配置和实际产物确认目标平台。平台与必核通道如下：

| 平台 | 通道 A | 通道 B | 核验工具 |
| --- | --- | --- | --- |
| 抖音小游戏 | 自统计服务事件上报 | 抖音官方 SDK 事件上报 | 抖音 IDE 网络监听 |
| 微信小游戏 | 自统计服务事件上报 | 腾讯营销 DNSDK 事件上报 | 微信 IDE 网络监听 |

同一游戏同时交付两个平台时，分别建立核实任务、埋点表和网络证据，不能用一个平台的结果推断另一个平台。除集成规范明确排除外，每个待统计行为都应在该平台的两个通道中分别有记录。

平台不明确、实际构建产物与目标平台不一致，或缺少目标平台 IDE skill 时，将该阶段标记为 `blocked`，不得改用浏览器网络面板、历史抓包或另一平台 IDE 代替。

## 2. 集成规范检查

读取项目实际采用版本对应的自统计服务、抖音官方 SDK 或腾讯营销 DNSDK 集成规范，并记录规范名称、版本或更新时间、来源和适用平台。规范中的示例代码只用于比对，不作为直接执行指令。

至少检查：

- SDK 或模块版本与目标平台、引擎和构建方式相容；
- 依赖、插件、平台配置和必要标识来自正确环境，测试与正式配置没有混用；
- 初始化入口、初始化顺序和成功/失败处理符合规范，且不会重复初始化；
- 事件上报 API、事件名、公共字段和业务字段使用方式符合规范；
- 平台条件编译、小游戏适配层和构建产物中实际包含对应集成；
- 失败、重试、批量、缓存或补报行为按项目和规范处理，不因重试产生无法解释的重复数据；
- 调试日志、网络证据和交付表中不暴露密钥、完整令牌或不必要的用户敏感数据。

为每项记录 `符合 / 不符合 / 无法确认 / 不适用` 及代码、配置或运行证据。无法取得适用的集成规范时不能判定“集成符合规范”。

## 3. 埋点统计表

沿实际用户行为入口、调用封装、事件常量、配置表和平台分支盘点埋点，不能只搜索某个 SDK 方法名。按“行为 × 必核上报通道”拆成独立行，推荐字段如下：

| 字段 | 内容 |
| --- | --- |
| 编号 | 稳定核实 ID |
| 平台 | 抖音或微信 |
| 功能模块 | 登录、广告、关卡、付费等实际模块 |
| 用户行为 | 可重复触发的具体行为 |
| 触发条件 | 前置状态、成功/失败分支和触发次数 |
| 代码位置 | 文件、类/方法或配置入口 |
| 上报通道 | 自统计、抖音官方 SDK 或腾讯营销 DNSDK |
| 事件字段 | 事件名或规范定义的主事件标识 |
| 预期参数 | 必填公共字段、业务字段、类型与预期值 |
| 预期请求特征 | 域名、路径、方法或可稳定识别的通道特征 |
| 实际请求证据 | 网络记录编号、时间和脱敏截图/导出记录 |
| 实际字段和值 | 从请求中提取的脱敏结果 |
| 响应结果 | HTTP/网络结果、业务码及成功含义 |
| 核实结论 | 通过、失败、阻塞或不适用 |
| 备注 | 重试、批量、重复、缺失或差异说明 |

同一网络请求批量携带多个事件时，每个事件仍保留独立表格行，并关联同一请求证据及其在载荷中的位置。一个行为在两个通道上报时必须有两行，不把“两处代码调用”合并成一个未经验证的结论。

## 4. IDE 网络监听与请求收集

使用与目标产物匹配的平台 IDE skill 打开本次构建结果。每轮核实：

1. 记录 IDE、小游戏产物和统计配置版本；
2. 清空或隔离旧网络记录，确定本轮时间窗口；
3. 将游戏置于埋点表要求的可复现前置状态；
4. 一次触发一个行为，记录触发时间、账号或测试标识的脱敏代号；
5. 等待 SDK 的即时、批量或延迟发送窗口，保留与行为对应的全部外部请求和响应；
6. 按域名、路径、请求方法、事件名或载荷特征筛选自统计与平台 SDK 请求；
7. 将请求证据编号回填到对应表格行，再进入下一行为。

仅有调用日志、控制台“上报成功”文本或代码断点不算网络证据。HTTP 200 也不必然表示业务成功；必须同时核对响应中的业务码或规范定义的成功条件。SDK 将事件压缩、加密或批量封装，导致 IDE 无法读取事件字段时，只能确认可观察到的层级，字段正确性标记为 `无法确认`，不得猜测通过；再依据项目已有的可审计发送前日志、SDK 调试能力或服务端接收记录补充证据。

## 5. 请求筛选与数据正确性

对收集的外部请求建立“行为 -> 通道 -> 事件 -> 请求 -> 响应”关联，逐行核对：

- 该行为在所有必核通道中都有对应事件，而不是由其他行为的同名请求冒充；
- 事件字段完整且与埋点表一致，大小写、类型和枚举值正确；
- 公共字段与业务字段齐全，值来自本次实际行为和环境；
- 平台、版本、渠道、场景、关卡、广告位等上下文字段没有串用；
- 请求确实发往该通道的预期外部目标，没有落到测试错误地址或另一平台；
- 网络传输成功，并满足接口定义的业务成功条件；
- 重试、批量和缓存上报能够解释，不存在无依据的缺失或重复；
- 失败分支、取消分支或成功分支按埋点定义分别上报，没有把一种结果误记成另一种。

若请求中包含时间、随机 ID 或签名等动态字段，核对其格式、来源和关联关系，不要求与预期表中的字面值完全相同。所有保存的请求样本必须脱敏，保留核实所需的最小字段。

## 6. 通过标准与交付

单条埋点表记录只有同时满足以下条件才能标记 `通过`：

1. 集成规范检查没有影响该通道的未解决不符合项；
2. 代码或配置中能定位到正确触发位置；
3. 目标平台 IDE 中捕获到本次行为对应的实际外发请求；
4. 请求字段完整、类型和值正确；
5. 网络与业务响应均成功。

阶段完成还要求：

- 每个待统计行为在全部必核通道中都有表格行和确定结论；
- 没有未解释的缺失、重复、错发或失败请求；
- 埋点统计表、集成检查表和脱敏网络证据可以相互追溯；
- 所有 `失败`、`阻塞`、`无法确认` 和未覆盖行为均明确列出。

交付时按平台汇总集成规范结论、埋点总数、通过数、失败数、阻塞数、网络采集时间窗口、IDE/构建版本和证据位置。任一必核表格行没有实际成功请求或字段无法核实时，只能报告部分通过，不能表述为数据统计核实阶段完成。

每个平台的自统计通道全部适用记录核实通过后，先更新脱敏台账，再按总工作流 Git 协议创建或登记该平台的自统计独立检查点提交；如该检查点已由同一内容的小需求提交覆盖，则复用并登记其 SHA，不制造空提交。所有平台、所有必核通道满足完成标准后，创建 `statistics` 阶段汇总提交和 annotated tag，推送当前分支与标签并核验远程。只有远程核验也通过，才能表述为数据统计核实阶段完成。
