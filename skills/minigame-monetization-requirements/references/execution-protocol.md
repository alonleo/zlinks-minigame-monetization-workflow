# 需求实现阶段执行协议

## 1. 执行台账与状态机

对每条规范化需求维护独立台账，建议保存在目标工程已有任务目录；没有约定时使用工程内 `.codex/monetization/<requirement-id>/`，但不要覆盖项目已存在的同名流程文件。

状态按以下顺序推进：

```text
extracted -> located -> experience-reviewed -> prompt-frozen
          -> implementing -> compiled -> built -> ide-verified -> done
```

可从任意执行状态进入：

- `blocked`：缺少决定实现或验证所必需的信息、能力或权限；
- `partial`：授权范围内已有可交付结果，但仍有明确未实现项；
- `not-applicable`：工程事实证明该条不适用，并附证据；
- `superseded`：来源需求已产生新版本，保留旧记录但不继续执行。

状态只在证据满足后推进。外部文档的“状态”是 `source_status`，不能直接作为执行台账状态。每条需求进入 `done` 后，按总工作流的 Git 协议更新台账并立即创建该需求的独立检查点提交，再开始下一条需求；提交 SHA 是该条回执的一部分。

## 2. 确认修改位置与内容

在读取经验和制定方案前完成：

1. 从实际入口追踪到场景、Prefab、脚本、配置、平台模板或远程资源；
2. 区分源资源、生成产物和平台导出产物，默认修改可再生的源，不手改下次构建会覆盖的产物；
3. 列出预计修改文件、运行时入口、受影响平台和不应改变的相邻行为；
4. 用示意图确认元素、相对位置和状态，不凭视觉相似度推断业务语义；
5. 记录现有未提交修改并避开无关内容。

定位结果不唯一时，不得进入实现。

## 3. 读取经验文档并预处理风险

按“项目级 -> 引擎/平台级 -> 功能级”的顺序查找经验文档，例如项目 `AGENTS.md`、构建说明、历史问题记录、广告接入说明和相关 skill references。只读与本需求有关的部分，但被选中的说明文件必须完整读取。

把经验转为方案中的具体动作：

| 经验类型 | 方案必须体现 |
| --- | --- |
| 会被生成器覆盖 | 修改源模板并增加构建后核对 |
| Unity 序列化易重排 | 保存前后检查差异规模和引用完整性 |
| 平台 API 存在差异 | 分平台实现或明确兼容层，不用一个平台结果替代另一个 |
| 广告回调可能重复/失败 | 幂等、防重、失败不发奖和恢复交互验证 |
| CDN 有固定前缀 | 上传前做信息表、工程配置、实际目标三方一致性校验 |

没有经验文档时记录搜索范围、缺失结果，以及基于工程现状采用的保守措施。

## 4. 冻结实施提示词

每条需求在改动前生成 `prompt-v<N>.md`。文本必须具体到可由另一个执行者复现，至少包含：

```markdown
# <requirement-id> 冻结实施提示词 v<N>

## 来源基线
- 信息表/游戏行：...
- 商业化文档/表格行：...
- 需求点原文：...
- 说明原文：...
- 示意图及用途：...
- 来源状态：...

## 工程事实
- 引擎与版本：...
- 目标平台：...
- 实际入口与修改位置：...
- 当前行为：...

## 要实现的结果
- 可观察行为：...
- UI/布局/文案：...
- 广告、存档、资源或平台规则：...

## 范围边界
- 必须修改：...
- 必须保持不变：...
- 不在本需求范围：...

## 经验约束与预处理
- 已读经验文档：...
- 已知问题：...
- 预防措施：...

## 执行方案
1. ...

## 验收标准
- 编译：...
- Unity CLI 或引擎验证：...
- 微信/抖音构建：...
- IDE 核验：...
- CDN 上传与引用：...

## 未知项与阻塞条件
- ...
```

冻结后记录来源文档的可用版本标识、更新时间或内容摘要哈希。实现期间发现工程事实不同，创建 `prompt-v<N+1>.md`，说明差异和影响，再继续；不得静默修改旧文件。

## 5. 实施与编译

- 按冻结提示词逐条执行，避免把一条需求的便利性修改扩散到其他需求。
- 脚本修改完成后使用项目实际引用和编译入口；资源修改完成后检查格式、编码、导入设置、GUID/引用以及生成步骤。
- 编译前先处理确定性的文本错误、缺失引用、条件编译和平台宏问题。
- 编译失败时保存本次命令、关键错误和受影响需求，修复后重新运行；不得删测试、关检查或使用旧产物掩盖失败。

## 6. 验证矩阵

| 改动类型 | 最低验证 |
| --- | --- |
| Unity 脚本或游戏端 UI/场景 | 脚本编译 + Unity CLI 使用正确版本执行可用验证入口 + 本次日志核对；布局需求还要有目标分辨率下的视觉证据 |
| 微信小游戏端代码/模板/配置 | 微信构建 skill 生成新产物 + 微信 IDE skill 打开该产物并核验需求相关行为和错误日志 |
| 抖音小游戏端代码/模板/配置 | 抖音构建 skill 生成新产物 + 抖音 IDE skill 打开该产物并核验需求相关行为和错误日志 |
| 多平台共享修改 | 各目标平台分别构建和 IDE 核验，不用单平台成功推断另一平台 |
| 广告策略 | 至少覆盖成功、取消/失败、不可用、重复触发和前后台恢复；模拟 Provider 结果必须明确不是实网验证 |
| CDN 资源 | 本地资源校验 + 增量上传 + 远端哈希或等价回执 + 构建产物/运行时 URL 引用核对 |

项目没有可用的构建或 IDE skill 时，不得临时杜撰自动化。记录已完成的静态/编译层证据，并把缺失层级标为 `blocked` 或 `partial`。

## 7. CDN 上传协议

只处理当前需求产生或明确指定的资源：

1. 从信息表读取 CDN 原始路径；
2. 从工程配置读取提供方、桶、基础 URL 和资源相对路径；
3. 由上传 skill 计算实际目标并展示三方对照；
4. 不一致时停止，不通过字符串拼接猜测线上目录；
5. 一致时执行增量上传，避免覆盖范围外对象；
6. 保存上传文件清单、大小、本地哈希、远端哈希或 ETag、目标键和时间；
7. 构建或运行核对引用指向新资源，缓存存在时按项目既有版本策略处理，不擅自全量清缓存。

七牛 Kodo 使用项目内的 [Kodo 上传 skill](../../minigame-kodo-upload/SKILL.md)。如果信息表指向其他提供方，必须使用对应 skill；没有对应能力时阻塞上传，不把文件复制到本地目录当作已上传。

## 8. 交付报告

报告按需求 ID 列出：

- 最终状态和冻结提示词版本；
- 实际修改位置、文件和可观察变化；
- 已读取的经验文档及采取的预防措施；
- 编译、Unity CLI、平台构建和 IDE 核验结果；
- CDN 文件与远端回执；
- 逐需求检查点 commit SHA；涉及自统计时列出各平台自统计检查点 SHA；
- 未执行、失败、模拟验证或需要人工/真机复核的内容。

全部适用需求成为 `done` 后，先更新阶段回执，再按 Git 协议创建 `requirements` 阶段汇总提交、annotated tag，推送当前分支和标签并核验远程。只有这些动作也成功时才能表述为需求实现阶段已完成。没有运行时证据时使用“静态检查通过”或“构建通过”等准确措辞。数据统计核实阶段按其独立协议执行，不能因本协议完成而宣称整个商业化流程完成。
