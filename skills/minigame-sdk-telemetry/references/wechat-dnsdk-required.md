# 微信 DNSDK：IAA 必报事件与参数门禁

## 范围与依据

这是用户根据 2026-10-26 提供的 DataNexus「IAA 小游戏」质量看板截图明确指定的接入要求，适用于 Cocos Creator 2.x/3.x 与 Unity 微信 DNSDK 接入和源码验收。不得把本表降为可选建议，也不得把 SDK 存在、方法定义、模拟测试通过当作业务已接线。

范围是微信 IAA 项目需要接入 DNSDK 时；抖音不适用。不因此自动开启通用模板默认关闭的开关、填入某个游戏的凭证、修改平台后台或发送生产事件。目标项目已明确要求 DNSDK 时，实际门控关闭或凭证缺失是接入失败，不能用模板默认关闭规避。

下表逐项覆盖截图的八个前置校验项和两个「有深无浅」配对项。截图不是完整官方协议：未列字段仍遵循当前厂商文档与实现契约，不擅自把自定义服务器字段加到腾讯 payload。

## 必检清单

| 编号 | 看板检查项 | 强制行为/字段 | 接入和源码验收要求 |
|---|---|---|---|
| DN01 | 归因开关 | 后台归因配置；SDK 有效开关、身份与初始化 | 当前微信 AppID/数据源正确，真实 OpenID 后初始化/注册，按现有契约启用 auto_track；后台归因必须开启。后台开关不是请求体字段，也不能用 auto_track=true 证明后台归因已开 |
| DN02 | 新手引导开始 | `tutorial_start` → `TUTORIAL_START` | 必须有真实开始调用且可达，首次开始一次并持久化；普通老用户回流不补造开始。没有独立教程时，把首次第一关实际开始作为教程开始、首次通关作为完成，不能启动时同时伪造两个事件 |
| DN03 | 通过关卡 | `level_success` → `LEVEL_PASS` | 真实胜利时必须上报；进入胜利 UI 本身不应导致重复结算。广告领奖等后续操作不重发同一结果 |
| DN04 | 通过关卡－关卡 ID 参数 | `LEVEL_PASS.action_param.level_id` | 必须存在且为从 1 起的正整数业务关卡号；与本局 LEVEL_ENTER 的 level_id 一致，不用内部表键、UUID 或写死的示例值 |
| DN05 | 进入关卡 | `level_start` → `LEVEL_ENTER` | 玩家实际进入关卡时必须上报，开始和结果沿同一局上下文；不能只定义接口或只往自定义服务器发事件 |
| DN06 | 关卡失败 | `level_fail` → `LEVEL_LOSE` | 真实失败时必须上报；主动退出发 LEVEL_EXIT，不冒充失败。确无失败机制须记录玩法证据和不适用原因，不能为了制造覆盖伪造失败 |
| DN07 | 进入关卡－关卡 ID 参数 | `LEVEL_ENTER.action_param.level_id` | 与 DN04 相同；业务资源号先统一映射。不要把 enter_level_id 当成 level_id；enter_level_id 的含义仍按已核对的厂商字段契约处理 |
| DN08 | 通过关卡－广告次数参数 | `LEVEL_PASS.action_param.ad_cnt` | 每条必须显式存在，为本局结果生成前完整看完激励视频的非负整数；由真实回调累计并从 ad_count 映射，不得缺参、发数字字符串、传固定示例数或以兜底 0 掩盖未接线 |
| DN09 | 新手引导有深无浅 | 开始 → 实际完成 | 开始/完成都要接到真实业务状态，第一个完整教程模块结束时尽早调用官方 onTutorialFinish()；跳过流程按游戏实际完成判定接入。已开始但未完成允许跨启动续接，不得仅为配对立即补造完成 |
| DN10 | 关卡有深无浅 | 结果必须先有同周期 `LEVEL_ENTER` | 开始后缺少结果允许存在，不能因此伪造结算；任何 LEVEL_PASS/LEVEL_LOSE/LEVEL_EXIT 必须有同一玩家、玩法、关卡和局/阶段的先行真实 ENTER。无开始、错周期、已结束周期的结果不得发送；自定义通道同样要求先 level_start，详见下节 |

截图 DN09 显示名是 `TUTORIAL_START → TUTORIAL_END`。当前 vendor 专用方法 `onTutorialFinish()` 产生 `TUTORIAL_FINISH`；保留该官方方法，不因看板文字自行改发 `TUTORIAL_END`，不同时补发两个名称。若厂商版本契约变化，先核对实际 vendor 和官方文档再调整。

## 强制：先开始，后结果（2026-10-29）

关卡链路按“有结果必须有开始”验收，不要求观测到的开始数与结果数永远相等。开始后没有结果可能是仍在进行、进程被杀、崩溃、断网或观察窗口截断；不能单凭缺少结果判定埋点顺序错误，也不得为凑齐链路补造胜负/退出。真实可观测胜利、失败、退出仍须按业务上报，已知结果路径未接线仍是缺项。

| 语义 | 自定义服务器事件名 | 腾讯 DNSDK action_type |
|---|---|---|
| 开始 | `level_start` | `LEVEL_ENTER` |
| 成功 | `level_success` | `LEVEL_PASS` |
| 失败 | `level_fail` | `LEVEL_LOSE` |
| 主动退出 | `level_exit` | `LEVEL_EXIT` |

不能把自定义事件改成 level_enter，也不能给腾讯直接发送 level_start。每条结果必须能追溯到同一玩家、同一玩法/模式、同一业务关卡和同一局/阶段的先前真实开始；“以前进过这一关”、其他局开始或仅设置全局 started=true 均不够。相同 level_id 在最终结算后再来一次仍是新周期；尚未结算的重开按下节场景 1 延续原周期，禁止混用两者。

- 业务门面和腾讯适配器都必须检查有效周期，覆盖便捷 API、通用 ReportEvent/track、直接桥接和异步回调。没有开始、关卡/模式不匹配、已结束周期的迟到或重复结果，不得作为有效结果发送；记录脱敏诊断并定位业务调用。不能仅检查方法声明或自定义 payload 中有 level。
- 分通道保证开始先提交、后提交结果。腾讯链路不能用“自定义已发 start”证明已发 ENTER；开始因开关、身份、初始化、过滤或调用失败未提交时，不允许结果绕过等待队列。关闭再启用、切换身份、场景恢复、旧持久队列和结果先到开始后到都需核查。
- 已经真实发生并已记录的开始，因网络失败可按原事件及顺序重试；禁止在 lose/pass/exit 前临时伪造 start/ENTER 来掩盖缺失。跨启动恢复须有可验证的原周期上下文；未结算复活不创建新周期，也不额外发送 ENTER。
- 正常单周期只接受一个最终真实结果。等待复活时不得提前发 LEVEL_LOSE；复活后延续原周期，最终失败、成功或退出才结算。已真正结算后继续玩必须显式建立新周期，不能借用旧周期的 ENTER。
- SDK 已接收不等于后台已送达。后台看到孤立结果属于异常链路，但可能是开始投递失败/延迟、时间窗口或身份/关卡错配，不能仅据一条后台记录断言业务没有调用开始；需联合调用和投递证据定位。

验收必须覆盖：仅开始无结果不误判；未开始直接 success/fail/exit 全部阻止；合法开始后每种真实结果正常映射；重复结果、跨关卡/模式、同关重玩旧回调不串局；身份未就绪先后事件保序；已最终结算后再来一次先发新 ENTER；未结算复活不得额外 ENTER。源码缺少保护或发现孤立结果可达路径判失败，无法证明的动态上下文列待确认，不能默认通过。只做规则更新时报告实现缺口，不把更新文档当成运行逻辑已修复。

## 四种场景的强制分流（用户确认口径，2026-10-29）

区分物理玩法重置与统计周期结束。本节按用户明确要求约束本套接入，不宣称 level_reStart 是腾讯原生标准事件；若旧模板实现与本节冲突，应报告并在获准修复时适配，不能声称模板已满足。

| 场景 | 自定义统计 | 腾讯 DNSDK | 周期状态 |
|---|---|---|---|
| 1. 游戏内尚未结算，点击重开 | 只上报 `level_reStart`，大小写固定；不发 level_start 或 success/fail/exit | 不为此发 ENTER/PASS/LOSE/EXIT，也不透传 level_reStart | 延续原统计周期，不清空原开始及累计计数；玩法可以重置 |
| 2. 已产生最终结算，点击再来一次 | 旧局结果只发一次；新关真正进入可操作状态时发 `level_start`，不以 level_reStart 替代 | 旧结果后，新局发 `LEVEL_ENTER`；不得二次结算旧局 | 建立新周期，重置广告数、有效时长基准与结果去重标志 |
| 3. 尚未最终结算，先弹复活并点击复活 | 不发关卡结果，也不重新发 level_start；确需记录复活动作可独立记录行为事件 | 不发 LEVEL_LOSE 或新 LEVEL_ENTER；复活广告的真实点击/曝光/完成仍按广告规则发 | 延续原周期，复活不清零计数，不重复初始化统计 |
| 4. 游戏内直接跳到另一关 | 若旧周期尚未结束，先发旧关真实结果，再在目标关真正开始时发 `level_start` | 旧关 PASS/LOSE/EXIT 在先，目标关 ENTER 在后 | 结束旧周期再建立目标周期；目标关不能沿用旧关的 ID、状态或计数 |

补充边界（均必检）：

- 结果事件只在最终结果确定时生成，不以“结算页是否已显示”作为唯一标准。复活弹窗/暂时死亡不是最终失败；拒绝复活、关闭复活弹窗后最终结束、复活失败后确认结束，才按真实结果发一次 fail；离开关卡按实际主动退出语义发 exit。
- 场景 1 必须已有同玩家/玩法/关卡的有效开始，且没有最终结果。已经结算再点重开归场景 2；未开始不能靠 level_reStart 伪造或补出开始。不得复用会先发结果的通用 clearGame/结算清理方法处理未结算重开。
- 场景 1 与 3 的广告完成数和有效游玩时长在同一统计周期内继续累计，不能随玩法重置清零或重置起点；后台/广告时间仍按原规则排除。不能把物理尝试次数当作 start/ENTER 次数。
- 场景 2 新关开始前若取消再来一次、加载失败或返回大厅，不提前伪造开始。连续点击/重试异步回调只能建立一次新周期；同关再次游玩也必须是新的统计周期。
- 场景 4 未通关的调试跳关/主动切关通常为 exit，不能为了跳过而伪造 pass；仅真实判定通关才用 success。旧局若已结算，不再补发第二个结果，只发目标关开始。同关尚未结算的重置归场景 1，不能把它误判为跳关；主动切换玩法/模式按实际周期切换处理。
- 四种场景均需使旧玩法异步回调失效，内部使用尝试版本/令牌或等效机制；只比较 level_id 不足以隔离同关的旧回调。该内部标记不自动添加到腾讯标准 payload。
- `level_reStart` 是独立行为：保留现有有效周期并记录该行为，绝不按普通通用事件“仅发一个名称”却丢失上下文。本套契约至少校验其业务 level 与有效周期一致；额外自定义字段按已接入协议定义，不在此擅加腾讯字段。
- 当前兼容 `reportLevelRevive/ReportLevelRevive` 若会映射腾讯 ENTER 或重置时间基准，不能直接用于场景 3。如旧实现已提前发 LEVEL_LOSE，就不能继续沿旧周期发送另一个结果；应修正失败触发点和复活状态流程，不能靠隐式补 ENTER 掩盖错误。

最小回归：初始 start/ENTER 后分别覆盖未结算重开、完整复活广告后恢复、拒绝复活最终失败、结算后再来一次、未通关跳关、通关后跳关。逐通道断言事件顺序与数量，未结算重开仅自定义 level_reStart、复活无关卡结果且无重复 ENTER、再来一次开始一次、跳关旧结果先于新开始，并核对累计值、重复点击及旧回调隔离。规则更新不能替代代码修复或实际渠道验收。

## 广告次数必须沿真实调用链取证

- 每次真正新局开始清零；完整观看成功回调只加一次。取消、报错、展示失败、未展示及免广告直接发奖都不加。
- 同一统计周期内复活和未结算重开均保留累计次数；最终结算后再来一次或切换到新关建立新周期时才清零。重复广告回调不得重复累加。
- 结果生成时保存次数快照再提交。胜利结算后才看的双倍领奖广告不得倒加到已经生成的本局结果，也不得为此重发 LEVEL_PASS。
- 必须核查业务 → 统计门面 → 腾讯适配器 → vendor 的最终 action_param，而不只检查 ad_count 出现在自定义 /v1/track。
- 真实零次观看时 `ad_cnt: 0` 正确；源码检查禁止“0 一律错误”，也禁止“默认是 0 所以完整”。找出计数变量、加一回调、新局重置、复活保留及结果取值的源码证据。
- 腾讯适配器只接受类型本身就是非负整数的 `ad_count`；不得把 `"1"` 等数字字符串转换为数字。缺失、字符串、负数、非整数或其他非法值统一输出数值 `ad_cnt: 0`，不得丢弃整条关卡结果；但源码验收仍将上游缺失/非法值列为 DN08 接入问题，不能用安全回落值证明真实计数已经接线。
- LEVEL_LOSE/LEVEL_EXIT 继续使用现有结果契约的真实广告计数；本轮截图特别要求 LEVEL_PASS 的 ad_cnt，不因此移除其他结果字段。

## 激励 placement 与播放链路

- 不发送按钮入口曝光事件。SDK 模板和项目都不得实现或调用 `ReportAdPlacementShown(...)`，不得产生 `ad_placement_show` / `AD_PLACEMENT_SHOW`。
- 每个固定点击入口必须传合法 placement 与当前入口解析后的中文 `prop_name`。固定入口禁止省略 placement、使用 Unknown/0 或把 `未知` 当作 prop_name。
- 若当前 dnSdk 契约只要求 `ad_placement_name` 为数字而没有规定业务语义对应的指定编号，SDK 必须校验后原样发送，不得增加“复活必须为 1、重玩必须为 16”等未经契约证明的转换。当前接入约束的有效范围为 1～67；不得上报 0、数字字符串、68 或其他越界值。
- dnSdk 激励播放链路是点击 `AD_CLICK`、广告真实展示 `AD_IMPRESSION(ad_type=1)`、完整观看 `AD_VIDEO_FINISH`。取消/错误不能产生完成事件，无广告直发不能伪造点击、曝光或完成。`prop_name` 属于自有/平台业务字段，不得混入腾讯只允许 `ad_placement_name` 的标准 payload。
- Unity 源码验收必须检查所有固定 `ShowAd` 调用已使用显式 placement 重载，禁止继续依赖三参数调用推断位置；门禁通过仍需微信渠道工具或真机验证实际送达。

## 两套统计必须隔离

- `tutorial_step` 仅平台/自定义通道，绝不进入 DNSDK。其 session、全局 step、中文 step_name 不进入腾讯新手引导动作。
- 自定义服务器的 ad_count 与腾讯的 ad_cnt 是映射关系；中文「剩余道具」「当前关卡」不能原样混入腾讯标准关卡对象。
- 本表描述强制最小检查项，不表示只有这些字段可以或必须存在。coin_amount、stamina_value、duration、items、game_mode 等仍按当前官方事件契约和实际业务提供，不把截图未列的字段臆断为全平台必填。
- 广告位置、曝光、开始/完成及结果去重等已有要求继续有效；新增门禁不能破坏合法腾讯行为、字段名称或类型。

## 最小验收证据

使用不联网模拟或已获授权的渠道测试，不删除真实存档。必须覆盖：

1. 新用户真实引导开始 → 第一个模块结束；开始与完成各一次，顺序正确，回流不重复；无独立教程时覆盖第一关方案。tutorial_step 不进入腾讯。
2. 业务内部 ID 映射到业务关卡 1、2；腾讯 ENTER 与 PASS/LOSE/EXIT 的 level_id 同局一致，覆盖胜利、失败、主动退出的真实可达路径。
   缺失、非法或尚未就绪的业务关卡号必须拒绝上报并记录脱敏诊断；禁止用 `|| 1`、`?? 1`、`Mathf.Max(1, ...)` 或同类兜底把错误数据伪造成第一关。自动用例必须同时证明第一关为 1、第二关为 2、缺失 ID 时没有任何腾讯关卡行为。
3. 一局完整观看 1 次、取消 1 次、失败 1 次，最终 LEVEL_PASS 的 ad_cnt 必须为数字 1；下一局未观看时为数字 0。
4. 同一广告完成回调重复不会加两次；同局复活后计数保留；免广告直发为 0；结算后的领奖广告不改写已发结果。模板已有案例可复用，但必须核对目标工程接线。
5. 对必填字段缺失、字符串广告次数、错误关卡映射、固定广告次数、只有接口无真实调用的情况，源码报告必须标为失败；动态值无法推出则列源码待确认，不能默认通过。

报告逐项列 DN01–DN10：预期、实际事件/字段、业务与适配器源码位置、测试证据、状态。DN01 后台归因、实际送达及看板质量只列外部验收提醒；没有后台证据不阻塞仅源码扫描结论，也不能据此宣称后台通过。截图标为异常的广告次数应优先复核，但不能在没有证据时断言原因就是固定 0。

HTTP code=0 或 SDK 同步返回成功只代表对应层接收，不能代替 IAA 看板质量通过。本表更新不授权构建、后台操作或生产上报。

## Debug 完成通知口径
